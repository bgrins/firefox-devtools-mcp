# Eval suite review — final report

Repo root: `/Users/bgrins/code/firefox-devtools-mcp`, branch `firefox-cli`.

## 1. Verdict

The suite is in good shape structurally and mostly clean: 38 fixture sites, 74 web tasks, per-site design languages that hold up under inspection (every one of the eight "these sites are the same design system" claims was refuted on direct inspection), and a golden-path verifier that keeps the tasks winnable. What is *not* in good shape is the grading layer. Roughly a dozen validators either accept a plainly wrong answer or reject a plainly correct one, and about eight tasks can be passed without doing the thing they exist to measure. The single most important thing to fix is **`price-compare`, `news-extract` and `variant-matrix` — three validators that grade a bag of substrings instead of the answer's actual claim, so each one passes an answer whose stated conclusion is wrong.** Those three are the clearest cases of the suite reporting a capability it did not measure. Right behind them: `gridword`'s answer word ships base64-encoded in the page, and `form-gauntlet`/`roster`/`modal-escape`/`canvas-pick` grade on facts a shell can fabricate from one page GET.

## 2. Confirmed defects, ranked by impact on validity

### Tier 1 — false passes: the task cannot distinguish a solve from a failure

1. **`/Users/bgrins/code/firefox-devtools-mcp/cli/eval/run.mjs:398-412` (`price-compare`).** The whole gate is `text.includes('274.50') && /NexBuy|ClaritySee/i`. The store conjunct is satisfied by the *product* name, so an answer attributing the win to Voltro or Gadgetron passes; `ANSWERS.priceCompare.perStore` is loaded and never read, so two thirds of the requested output is ungraded; and an answer naming an out-of-stock decoy as the overall winner passes as long as `274.50` appears somewhere in its table. The out-of-stock filter is the task's entire reason to exist, and Gadgetron's stock cell is the one that sits behind the A3/A13 tool gaps — i.e. the one store the validator ignores is the one that would show the mcp-vs-playwright separation. Fix: require the winning product **and** store in the same clause as the price, grade the three `perStore` figures numerically with tolerance, and veto naming a sold-out listing as the choice (copy `oos-substitute`'s `namesDecoyAsChoice`).
2. **`cli/eval/run.mjs:1462-1477` (`news-extract`).** Three independent whole-answer `includes()` per row, no row binding. A table with the points column rotated one row scores 20/20; swapping the points and comments columns scores 20/20; emitting ranks 2-21 instead of 1-20 scores 19/20 and passes. Six of twenty comment counts are single digits, so `includes('7')` is satisfied by any stray 7 — the column can be fabricated as a constant and still score 20/20. Fix: parse the answer into rows and require title/points/comments to co-occur within one row (`rate-limited-lookups`' `pairOk` is the existing pattern).
3. **`cli/eval/run.mjs:2679-2730` (`variant-matrix`).** `sizeOk`/`colorOk`/`priceOk` are three independent bag-of-words tests. An answer that declares the *most expensive* combo (L/Moss $52.00) as the winner and then prints the 9-row matrix passes. Worse, the same trick defeats the documented decoy trap: declaring the out-of-stock S/Moss $34.00 as the winner passes, because `M`, `Sand`, `39.50` and "out of stock" all appear elsewhere in the matrix. Fix: bind size+colour+price to the clause carrying the superlative, and reject a clause that names a different combo as the choice.
4. **`cli/eval/pages/gridword/index.html:301` + `cli/eval/run.mjs:333-341` (`gridword`).** `atob('Q1JJU1As…')` decodes to the answer list; `?day=0` is `CRISP`, verbatim `ANSWERS.gridword.day0Word`. Easy mode makes no server request at all, so there is nothing to gate on, the whole validator is one case-insensitive unanchored regex, the ask's "how many guesses you used" is ungraded, and `CRISP` is an ordinary English adjective ("the autumn air was crisp" passes). No recorded run exploited it (36/36 played honestly), which is why this is major rather than blocker. Fix: route easy mode through `/api/gridword/guess` with the word held in `server.mjs` like `hardDay3`, grade `won === true` and the reported count, and word-boundary the regex.
5. **`cli/eval/server.mjs:7086-7111` + `cli/eval/pages/canvas/swatch.html:133` (`canvas-pick`).** `/api/canvas/reveal` pushes the graded beacon *before* checking the cell, has no rate limit, and the validator only asks whether `C4R2` appears in any pick — so a blind 48-cell POST sweep passes with zero canvas interaction and zero comprehension. Independently, `PALETTE` is inline in the page, so `#e8850c` at row 2 / col 4 gives the answer from a plain curl. Fix: mint the palette server-side per session, and reject a session that swept (or grade only the first pick). A Referer gate will not help — `server.mjs:2315` already documents that `curl -e` defeats those.
6. **`cli/eval/server.mjs:6767`/`6790` (`modal-escape`).** `/api/modal-shown` and `/api/modal-dismiss` have no `fromPage`/sec-fetch gate, unlike the twelve endpoints in the same file that do, and no `offPage` counter — so a forged pass is byte-identical in `detail` to a real one. Two curls plus the static `items.json` title pass the task. Fix: add the provenance gate used at `server.mjs:5627`, and mint a per-show dismissal token in the modal DOM that the dismiss POST must echo.
7. **`cli/eval/run.mjs:429` (`form-gauntlet`).** Both graded facts are fabricable. `ANSWERS.form.refCode` = `MD-4921` is computed on disk at `cli/eval/pages/forms/index.html:374`; the interaction gate is a `form-progress` beacon that the generic `POST /api/beacon` mints from the page nonce — or, more simply, one `evaluate_script` calling the page-global `progress(3)`. Zero fields filled, zero clicks, validator passes. This contradicts the invariant stated at `server.mjs:3-4` and the five in-file comments that deliberately keep forgeable beacons *out* of pass decisions. Also worth noting: the nine field values the ask dictates are never checked at all. Fix: mint the review-step code per session, record step progression on a dedicated route, and put the collected `data` on the step-3 record so the data-entry half is graded.
8. **`cli/eval/run.mjs:498` + `cli/eval/server.mjs:8033` (`roster`) — two defects.** (a) The graded group code is `'GRP-' + session.nonce.slice(0,4).toUpperCase()` and the nonce is printed in the served page, so it is computable from one GET; the interaction gate is another forgeable `roster-submit` beacon; the "Add attendee" growth the ask names is not observed at all. (b) `submits.length === 1` counts beacons **globally across the run** with no winner selection, so any second submission anywhere hard-fails a correct run — and because `good = submits.find(...)` takes the *first* match, a curl probe session's nonce can supply the graded code while the browser is shown a different one. Loosening the count alone does not fix it. Fix: record the submission on the session from `/api/roster-submit` only, mint the code from `randomBytes`, and select the winner session the way nine other validators in this file do.
9. **`cli/eval/pages/shop/gadgetron/gadgetron.js:73` (`oos-substitute`) — false *fail* on good reasoning.** Every catalog row's "BUY IT NOW" button is a client-side lie: it bumps a local counter and relabels itself "Queued" without ever calling `/api/shop/cart/add`. An agent that correctly finds PF-27 sold out, reads the substitution table and queues BP-27U from the catalog row gets an affirmative success message while the graded server order list stays empty. The mitigating notice ("Part numbers are queued from the order list page") is truncated by A2 in our own snapshot while 24 enabled buy buttons are not — and Voltro and NexBuy's equivalent buttons *do* post, so gadgetron is the only store whose buy control lies. Because playwright's snapshot carries the table rows and ours does not, the better snapshot is more likely to click the lying button, biasing the comparison the suite exists to make. Fix: wire the handler to `/api/shop/cart/add`, or replace it with a link to `order-list.html`.

### Tier 2 — false fails: correct answers rejected

10. **`cli/eval/run.mjs:3108-3122` (`pr-review`).** `alsoNamed.length === 0` auto-fails any answer that mentions another candidate identifier, with no clause split and no negation handling — unlike `breadcrumb-sibling`, `search-decoy`, `oos-substitute` and `canvas-log`, which all have that guard. `strictRe('cache-key')` is `tariff[\s_.\-]*class` and `tariffClass` is the parameter name of the enclosing function for two of the four defect variants, so `"src/tariff/quote.js:36, inside quoteFor(laneId, tariffClass, units, table), the total uses rate.perTonne"` — a correct, non-hedging report — fails. Fix: match the camelCase token only, or require the rival identifier to sit in a fault-attributing clause.
11. **`cli/eval/run.mjs:873-925` and `:929-983` (`breadcrumb-sibling`, `search-decoy`).** The per-clause misattribution check splits on `[.!?\n;:,]` plus five conjunctions; em dash, parentheses, slashes, arrows and middots are not separators (and the validator folds the dash family to `-` for *number* matching without making `-` a boundary). Correct contrastive answers — the shape the `search-decoy` ask actively invites ("careful: NOT Form RV-7A") — are graded as swaps. Worse, the existing `:` separator can strand a number away from its own desk name and manufacture a false swap. Fix: add dash/paren/slash/bullet boundaries, or require the decoy value and the decoy name to be adjacent before calling it a swap.
12. **`cli/eval/run.mjs:3722-3726` (`canvas-log`).** `decoys.length <= 1` fails a maximally correct answer that attributes all four ERROR ids to their own steps — which is exactly what the site's own escape hatch produces, since searching for "ERROR" renders all four on one screen. Two validators away, `office-finder` and `media-transcript` already implement the right pattern with comments explicitly rejecting a blunt decoy count. Fix: only count a decoy that is *not* attributed to its own step, or bind the check to the claim sentence.
13. **`cli/eval/run.mjs:3646-3663` (`live-auction`).** The decline branch derives `nextRung` from `hammerPrice`, which `auctionTick()` writes only after the 150 s floor expires. An agent that correctly works out the next rung breaches its limit, declines and reports immediately is graded `hammerPrice=null → forcedOut=false → fail`; 152 s later the byte-identical answer passes. Frequency-gated to the 1-in-9 ceiling=1800 draw. Fix: derive `forcedOut` from `a.price + A.increment` (identical discrimination, no timing dependency). Two smaller companions on the same branch: `declinedOk` requires the *refused* rung while the ask says "the figure we stopped at", and `saidStopped` is a closed verb whitelist that rejects the ask's own phrase "let the lot go" (accepts only "let it go").
14. **`cli/eval/run.mjs:2426-2430` (`modal-escape`).** The truncation workaround does not survive truncation: the comment says the fallback exists because the snapshot clips titles at 27 chars, but the chosen phrase `/spreadsheet that compiles/i` spans chars 10-35 and is absent from the clip. This false-fails *our* condition specifically, since playwright's snapshot is untruncated. Fix: fall back to `/spreadsheet/i` or `/webassembly|wasm/i`.

## 5. Coverage honesty

- **Everything in section 4 is unverified.** Those items were reported once and not independently reproduced. Expect some to be wrong in the same ways the refuted majors were wrong (mis-cited line numbers, evidence assembled from source rather than from what an agent sees).
- **No full sweep was run.** No condition comparison, no token/cost measurement, no pass-rate data was produced by this review.
